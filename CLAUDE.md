# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Rust terminal (ratatui) AI language tutor. Exercises, curriculum, and answer analysis are generated by an LLM provider the user configures (OpenAI, Anthropic, Google, DeepSeek, Mistral, OpenRouter, Ollama, or a custom OpenAI-compatible endpoint via `rig-core`). Data is stored locally per language pair in LanceDB tables under `.open-course-cli/`, and can optionally sync to the cloud (see Sync below).

Read `README.md` for install/usage and `docs/flow.md` for the full user-facing flow (onboarding, dashboard, session lifecycle, settings, account/sync) — both are kept current and are the source of truth for behavior, not just this file.

## Commands

```bash
cargo run -p open-course-cli                     # run the TUI (data in ./.open-course-cli/)
cargo run -p open-course-cli -- --data-dir /path # run against a different data dir
cargo test --all-features                        # run all tests (workspace)
cargo test -p open-course-cli --test session_test # run a single test file
cargo test some_test_name                        # run a single test by name
cargo clippy --all-targets --all-features -- -D warnings  # lint (mirrors CI)
cargo fmt --all                                  # format (mirrors CI)
python3 scripts/debug_exercises.py               # debug LLM exercise generation directly
```

Set `OPEN_COURSE_CLI_DEBUG=1` to enable debug event logging (see `crates/llm/src/debug_log.rs`, `crates/llm/src/pipeline.rs::log_debug_event`).

## Workspace layout

The repository is a Cargo workspace with a one-directional dependency graph:

```
core ← {config, db}
{core, config} ← llm
{core, db} ← sync
{core, db, llm, config} ← service
{core, db, llm, config, service, sync} ← cli
```

- `crates/core` (`open-course-core`) — pure domain: types (`Topic`, `ProgressTopic`, `SessionSummary`, `LearningItem`, all with `updated_at`/`deleted_at` for sync), session orchestration, scoring, dashboard stats, `AppError`/`Result`. No DB, no UI.
- `crates/db` (`open-course-db`) — LanceDB tables, Arrow converters, `Database`, the schema-migration registry, and the sync outbox.
- `crates/config` (`open-course-config`) — `OpenCourseConfig`, profiles, providers, on-disk config migrations.
- `crates/llm` (`open-course-llm`) — LLM clients, prompts, parsing, retry/streaming, diagnostics; also owns the `LlmResult` enum (moved here from the app to break the app↔llm cycle).
- `crates/service` (`open-course-service`) — the service layer: business logic shared between the CLI and any future frontend (e.g. an HTTP server).
- `crates/sync` (`open-course-sync`) — cloud sync client: defines the wire protocol the future server must implement, plus the token store.
- `crates/cli` (`open-course-cli`) — the `opencourse` binary: event loop, views, widgets — a thin adapter over `service` and `sync`.

### Event loop and state (`crates/cli/src/app/mod.rs`)

Single-threaded async event loop in `run_app`. One `AppState` struct holds the current `View` enum plus one state struct per view (`DashboardState`, `SessionState`, `CurriculumState`, etc. — all in `crates/cli/src/ui/views/`). Each loop iteration:

1. Draws the current view (`draw()` matches on `state.view`).
2. Kicks off pending background work (e.g. auto-loading session topics/curriculum when a view needs them but has none loaded).
3. `tokio::select!`s over four sources: terminal input (`EventStream`), an `mpsc::Receiver<LlmResult>` for async LLM responses, an `mpsc::Receiver<SyncMessage>` for async sync/account work, and a 100ms tick (only redraws when a view is actively waiting — `redraw_on_tick`).

Key/mouse handling dispatches to a per-view module (`dashboard::handle_key`, `session::handle_key`, etc. in `crates/cli/src/ui/views/`), which mutate `AppState` directly and return `Result<()>`.

Two background-result channels exist side by side:

- **LLM**: tasks send an `LlmResult` variant (`Exercises`, `Analysis`, `Curriculum`, streaming chunks, diagnostics, ...) through `llm_tx`; `app/llm_results.rs::apply_llm_result` applies them — the single place async LLM results reach `AppState`. Add new LLM-backed features there.
- **Sync/account**: tasks send a `SyncMessage` variant (`DeviceFlowStarted`, `LoginFinished`, `BindScenarioLoaded`, `SyncFinished`, `CurriculumConflict`, ...) through `sync_tx`; `ui/views/settings/account.rs::apply_sync_message` applies them. Add new async sync features there rather than blocking the event loop.

### Views (`crates/cli/src/ui/views/`)

Each view is a module exposing `draw()` and `handle_key()` plus a `*State` struct owned by `AppState`. Views: `onboarding` (multi-step wizard, own `state.rs`/`steps.rs`/`handlers.rs` submodules), `dashboard`, `session`, `docs`, `report`, `curriculum`, `settings` (own `fields.rs`/`data.rs`/`provider_setup.rs`/`account.rs` submodules), `model_check`, `pairs`, `update`. Shared widgets (activity calendar, sparkline, progress bars, spinner, markdown rendering) live in `crates/cli/src/ui/widgets/`.

Mouse wheel scrolling is only enabled on views without text input (`view_supports_mouse`); `m` toggles mouse capture off for native text selection.

### Service layer (`crates/service/`)

Business logic lifted out of views and result handlers so the CLI (and a future server) stay thin adapters:

- `session.rs` — session flow: `prepare_exercises` / `generate_session_exercises`, `next_session_topic`, `prepare_analysis` / `run_session_analysis`, and `apply_analysis` (ensures new topics/progress, applies scores, returns neutral `AppliedAnalysis` for the UI to render).
- `curriculum.rs` — generation/extension of the curriculum, `persist_topics`, `delete_topic`, `load_curriculum`, `reset_curriculum_data`.
- `reset.rs` — `ResetAction` + `execute_reset`.

Service functions also write the sync outbox hooks (upsert/delete/tombstone-reset entries) after each mutation of a synced entity, best-effort.

### Core domain logic (`crates/core/`)

- `session/` — session orchestration: `topic_selection.rs` implements `pick_next_session_topic` (balances new curriculum topics vs. spaced-repetition review, roughly 1-in-3 sessions is a review, more when many topics are due), `scoring.rs` (mastery decay ~5%/day), `models.rs` (shared types like `Exercise`, `AnalysisResult`). Applying analysis to the DB lives one layer up, in `open_course_db::apply` (it needs the tables).
- `dashboard.rs` — aggregates progress/history into dashboard stats (weak topics, activity calendar buckets).
- `curriculum.rs` / `progress.rs` / `history.rs` / `learning_items.rs` / `reviews.rs` — domain types and pure helpers (CEFR mapping, dedupe, slugify, `topic_id_from_name`).
- `language.rs` — ISO 639-1 language code handling.
- `error.rs` — `AppError`/`Result` used by all crates.

### Persistence (`crates/db/`)

One LanceDB-backed table module per concern: `curriculum.rs`, `progress.rs`, `history.rs`, `reviews.rs`, `learning_items.rs`, plus `metadata.rs`, `outbox.rs` and `util.rs` helpers. `Database` (in `crates/db/src/lib.rs`) owns one instance of each table and is cheap to `.clone()`. Each language pair gets its own `Database` connected to `.open-course-cli/pairs/{native-target}/db/`; switching pairs (`app::switch_pair`) reconnects and replaces `state.db`.

**Schema migrations** (`migrations.rs`): the pair's schema version is stored in the metadata table (`schema_version`, absent = 1); `Database::connect` runs the versioned registry up to `CURRENT_SCHEMA_VERSION` (currently 4: v2 `updated_at`/`deleted_at` columns, v3 UUIDv7 session ids, v4 outbox table). Older ad-hoc migrations in the tables' `open` functions are idempotent no-ops afterwards.

**Sync-shaped tables**: upserts stamp `updated_at` (with `*_with_timestamps` variants that write rows verbatim for sync pull), deletes are soft (tombstones filtered from reads, `purge_deleted` for future GC), and `outbox.rs` logs every synced mutation with a monotonic `seq`. The metadata table also holds the sync cursors (`last_pulled_seq`, `sync_enabled`, `cloud_curriculum_version`, `last_sync_at`); its `reset` preserves those service keys.

### LLM integration (`crates/llm/`)

- `client.rs` / `factory.rs` — `LlmClient` trait and `RigClient` (built on `rig-core`); `create_llm_model` builds a client from the active provider config.
- `provider.rs` — provider enum/metadata (OpenAI, Anthropic, Google, DeepSeek, Mistral, OpenRouter, Ollama, Custom) and per-provider defaults.
- `prompts.rs` — prompt templates for curriculum, exercises, analysis, topic docs.
- `pipeline.rs` — request orchestration and debug logging.
- `streaming.rs` — streamed response handling (used for curriculum generation progress and text streaming).
- `parse.rs` — parsing/validating structured LLM output (exercises, analysis, curriculum JSON) with `schemars`-derived schemas.
- `diagnostics.rs` — the onboarding "model check" pipeline (connectivity, streaming, exercise generation, analysis, topic review), driving `ModelCheckState`.
- `model_listing.rs` — fetching available models per provider for onboarding/settings.
- `retry.rs` / `transport.rs` — retry policy and HTTP transport config.
- `result.rs` — the `LlmResult` enum used as the app's LLM-result channel message.

### Config (`crates/config/`)

`OpenCourseConfig` holds provider settings and preferences (global), a `profile.rs` per language pair (native/target language, age, CEFR level), the `active_pair` id, and an optional `sync` block (`serverUrl`, `accountEmail`, `deviceId` — never the token). `provider.rs` holds per-provider config (API key, base URL, model, endpoint kind). `migration.rs` handles one-off upgrades of on-disk state between versions — these run once at startup in `main.rs` and are gated by marker files so they don't re-run.

### Sync (`crates/sync/`)

The sync client crate defines the protocol the future server must implement (camelCase JSON, additive changes only): device-flow auth (`POST /auth/device`, `POST /auth/device/poll`), `POST /v1/sync/push`, `GET /v1/sync/pull`, `GET /v1/me`. `SyncClient` handles timeouts (10s regular, 2.5s pull-on-start), bearer auth, retry with backoff on network/5xx, 401 → `Unauthorized`, 409 → `PushError::CurriculumConflict`.

- **Engine** (`engine.rs`): `push` drains the outbox (only after server confirmation — repeats are safe), `pull` applies changes with per-row last-writer-wins on `updated_at` (missing local timestamp = oldest; ties and implausible future local timestamps go to the incoming row).
- **Binding** (`bind.rs`): `first_bind_choices` (FreshLocal/FreshCloud/Conflict), `adopt_cloud_curriculum` (take the cloud canon, tombstone local topics not in it, optional progress wipe that bypasses the outbox) and `replace_cloud_curriculum` (push local topics as the new canon with `forceCurriculum` and version `max(cloud, local)+1`).
- **Tokens** (`tokens.rs`): `TokenStore` keeps the access token in the OS keychain when available, falling back to a 0600 `auth.json` in the data dir (the UI warns about the file backend). Tokens never touch the config file.
- The server URL comes from `resolve_sync_server_url` (config crate): env `OPEN_COURSE_SYNC_URL` > `config.sync.serverUrl` > `https://api.opencourse.app`.

## Testing conventions

Tests live in `crates/cli/tests/` as integration tests (one file per concern: `config_test.rs`, `db_test.rs`, `dashboard_test.rs`, `session_test.rs`, `settings_layout_test.rs`, `prompts_test.rs`, plus `debug_*`/`layout_debug.rs` exploratory harnesses). They use `tempfile` for isolated data dirs and drive real `AppState`/`Database` instances rather than mocking — prefer the same style for new tests (construct real state, assert on behavior, not on internals). Unit tests live next to the code in `crates/{core,db,llm}/src/`. The sync crate has contract tests in `crates/sync/tests/contract.rs` against a stateful in-memory mock server (axum on localhost) — no real network in tests.
