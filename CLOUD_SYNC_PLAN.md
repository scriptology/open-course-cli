# План: облачная синхронизация и серверная часть

Цель: опциональная синхронизация локального прогресса с сервером, axum-бэкенд для будущего мобильного приложения (платная подписка). Весь текущий функционал CLI остаётся полностью автономным и не зависит от облака.

## 1. Граница public/private: workspace + git-зависимость

Публичный репозиторий превращается в Cargo workspace:

```
open-course-cli/
├── crates/
│   ├── core/      # домен: сессии, скоринг, выбор тем, DTO (serde) — без UI
│   ├── db/        # LanceDB-слой + типы ProgressTopic, LearningItem...
│   ├── llm/       # промпты, клиенты провайдеров, retry-пайплайн
│   ├── config/    # конфиг, профиль, провайдеры
│   ├── sync/      # клиент синхронизации (публичный)
│   └── cli/       # app + ui + event, бинарь opencourse
```

Приватный репозиторий `opencourse-server` — axum-сервис, зависящий от публичных крейтов:

```toml
open-course-core = { git = "https://github.com/you/open-course-cli", tag = "core-v0.7.0" }
open-course-llm  = { git = "...", tag = "core-v0.7.0" }
```

Зависимость идёт только в одну сторону: приватное → публичное. Позже крейты `core`/`llm` можно публиковать на crates.io (зависимость от версий вместо тегов).

**Лицензия**: в репо сейчас нет LICENSE. Для модели «открытое ядро + платный сервис» нужна MIT или Apache-2.0 (позволяют закрытому серверу линковаться с открытым кодом; GPL мешала бы). Добавить до приёма внешних контрибуций.

## 2. База на сервере: Postgres, не LanceDB

LanceDB — embedded, single-writer; для мультитенантного сервера не подходит. Данные реляционные по природе (плоские строки, векторный поиск нигде не используется). Сервер использует Postgres со своей реализацией хранилища над общими типами домена из `core`; pgvector закроет векторные сценарии в будущем.

Синхронизация — на уровне сущностей, не файлов:

```
POST /v1/sync/push   { pair_id, progress: [...], sessions: [...], items: [...] }
GET  /v1/sync/pull?pair_id=...&since=...
```

Семантика: `session_history` — append-only (тривиальный мерж), `progress`/`learning_items` — upsert по id с `updated_at` + last-write-wins per row. В публичные типы добавить `updated_at` (обратно-совместимое изменение схемы).

## 3. Логин из CLI: device flow (как `gh auth login`)

1. В настройках CLI — «Войти». CLI вызывает `POST /auth/device` → получает код и ссылку `https://opencourse.app/connect?code=XXXX`.
2. Показывает ссылку (и пытается открыть браузер). На сайте — регистрация/логин по email+паролю, подтверждение кода.
3. CLI поллит `POST /auth/device/poll` → получает access token, сохраняет в `~/.open-course-cli/auth.json` (права `0600`).
4. Sync идёт с `Authorization: Bearer`.

Тот же auth и API покрывают будущее мобильное приложение.

## 4. Что сервер переиспользует из публичного кода

- Промпты и retry-пайплайн (`llm`) — генерация упражнений/анализа на сервере для мобильного приложения.
- `core/session/models.rs` — serde-совместимые DTO, готовая схема HTTP API.
- Скоринг и выбор тем (`core`) — тот же адаптивный движок, что в CLI.
- На сервере LLM-токены оплачены подпиской; CLI остаётся BYOK без зависимости от облака.

## 5. Рефакторинг публичного репо

1. Разбить на workspace-крейты (п. 1) — механический шаг.
2. Перенести `LlmResult` из `app` в `llm` (или заменить на callback) — убрать обратную зависимость.
3. Поднять логику флоу из `handle_key` вьюшек (напр., session flow в `src/ui/views/session.rs`) в сервисные функции `start_session(db, config) -> MentorSession`, `submit_answers(...) -> AnalysisResult`. CLI и axum-handlers — тонкие адаптеры.
4. `updated_at` в сущностях прогресса.
5. Публичный `sync`-крейт: очередь изменений / state-diff, push/pull, конфликты, работа офлайн. Публичность sync-клиента — плюс для доверия (видно, какие данные уходят с машины).

## 6. Рассмотренные альтернативы

- **Supabase/Firebase** — быстрый старт, но LLM-логика и переиспользование `core` ложатся плохо, vendor lock-in на самом ценном месте. Нет.
- **PowerSync / ElectricSQL** — sync-движки поверх Postgres. Интересно на этапе мобильного приложения, сейчас overkill.
- **Файловая синхронизация lance-директорий** — это backup/restore, не sync: конфликты неразрешимы, мобилка ничего не запросит. Нет.
- **CRDT (Automerge)** — избыточно при last-write-wins-допустимых данных. Отложить.

## 7. Две машины: флоу синхронизации и подводные камни

Сценарий: один аккаунт, CLI на машине A и машине B, обе работают с одной языковой парой.

### Базовый флоу

1. **Привязка устройств.** Каждая машина проходит device flow независимо и получает свой токен (`device_id` + имя устройства, отображается на сайте, отзывается отдельно). Аккаунт один, устройств много.
2. **Пространство данных** — `user_id + pair_id`. `pair_id` детерминирован (`{native}-{target}`), поэтому обе машины естественно попадают в один namespace без дополнительной настройки.
3. **Первая синхронизация пары.** Машина, которая первой включила sync для пары, загружает curriculum + прогресс целиком; curriculum становится **каноническим** на сервере (см. камень №1).
4. **Установившийся режим:**
   - pull при старте CLI (если залогинен и онлайн);
   - push после каждой завершённой сессии (и после генерации curriculum/доков);
   - ручная команда «Синхронизировать» + статус «последний sync» в настройках;
   - офлайн: изменения копятся в локальном outbox, пушатся при появлении сети.
5. **Механика pull.** Сервер ведёт журнал изменений пары с монотонным `revision` (seq); каждое устройство хранит курсор `last_pulled_seq` → дельта-пулл только новых строк. Полная перезагрузка — только при первой привязке устройства.
6. **Механика push.** Локальный outbox изменённых строк (с `updated_at`); сервер применяет LWW per row и возвращает новый `revision`.

### Подводные камни и решения

1. **Расхождение curriculum — главный камень.** Curriculum генерируется LLM локально: если машины A и B независимо сгенерируют программу для одной пары, наборы тем будут *разными*. Id тем придумывает LLM (обычно слаги из названий; `sanitize_curriculum_ids` — только repair при битом JSON, коллизии закрываются суффиксами `-1`/`-2` в `analysis.rs`), т.е. совпадение id между машинами вероятно, но **не гарантировано**; состав в целом разойдётся.
   - Решение: curriculum — sync-once сущность. Первая машина пушит, сервер помечает каноническую версию. Машина B при создании той же пары видит «пара уже есть в облаке» и **подтягивает облачную программу вместо генерации** (выбор: облачная / сгенерировать свою и заменить каноническую).
   - Если обе машины создали пару офлайн до первого sync — настоящий конфликт: при первом пуше B сервер отвечает 409, CLI предлагает выбор канонической версии. Прогресс по темам, совпавшим по id, сохраняется; «осиротевший» прогресс не удаляется, а помечается неактивным (темы нет в канонической программе).
   - Регенерация curriculum — явное действие пользователя, новая `version`, пушится как новая каноническая.
2. **Id сессий не глобально уникальны.** Сейчас `SessionSummary.id = Utc::now().timestamp_millis()` — две машины могут сгенерировать одинаковый id.
   - Решение: перейти на UUIDv7 (time-ordered, сортируемые, удобны для истории). Сервер дедуплицирует push по id (идемпотентность: повторный пуш той же сессии — no-op).
3. **Параллельная практика одной темы на двух машинах.** EMA-mastery обновится на обеих независимо; LWW per row затрёт одно из обновлений.
   - Решение MVP: принять. Прогресс самовосстанавливается — следующая сессия пересчитает EMA от актуального значения; потеря одного апдейта статистически незаметна. Sync-on-start + push-after-session сужают окно конфликта до минут.
   - Фаза 2 (если понадобится точность): хранить результаты сессий как append-only события и пересчитывать mastery сервером (event sourcing). Не делать в MVP — требует хранить детали анализов.
4. **Рассинхрон часов между машинами** ломает LWW по клиентскому `updated_at`.
   - Решение: порядок определяет серверный `revision`; `updated_at` клиента используется для LWW только внутри одной строки, при ничьей/аномалиях (updated_at далеко в будущем относительно серверного времени) побеждает запись с большим серверным revision.
5. **Сброс прогресса / удаления воскресают после pull.** Локальный reset удаляет строки; сервер про это не знает и вернёт их обратно.
   - Решение: tombstones — reset пишет маркер `reset_at: timestamp` в metadata и пушится как операция; сервер удаляет все строки пары старше маркера и раздаёт маркер другим устройствам. То же для точечных удалений (темы): `deleted_at` вместо физического удаления, GC позже. Учесть: `progress.reset()` сейчас стирает заодно metadata (`session_count`, `adaptive_alerts`) — маркер должен инвалидировать и её; `learning_items` вообще не сбрасывается ни одним `ResetAction` — отдельно решить, входят ли items в reset и tombstone-семантику.
6. **Learning items мержатся хорошо бесплатно.** Id детерминированы (`{lang}-{slugify(name)}`), т.е. одна и та же фраза на обеих машинах — одна строка; конфликт решается LWW, практика суммируется естественно. Отдельной работы не требует.
7. **Reviews (LLM-доки по темам)** — кэш, регенерируется из канонической темы.
   - Решение: в MVP не синкаем (экономим трафик и хранение); при желании — опциональный blob-sync позже.
8. **Приватность: что реально уходит на сервер.** Ответы пользователя и тексты упражнений остаются локально — `SessionSummary` хранит только оценки и id тем. Синкаем: curriculum (темы), прогресс, историю сессий (оценки), learning items (слова/фразы — учебный контент, не свободный текст), метаданные. Это стоит явно перечислить в UI настроек («что синхронизируется») — доверие для open-source продукта.
9. **Офлайн-очередь.** Без неё push-after-session падает молча и изменения теряются до следующего полного цикла.
   - Решение: outbox-таблица (lance) с операциями upsert/delete + retry с backoff; статус очереди виден в настройках («3 изменения ожидают синхронизации»).
10. **Дубли при повторных пушах** (retry после таймаута, когда сервер уже применил).
    - Решение: идемпотентность — сервер дедуплицирует по id сущности + `updated_at`; сессии — по UUID.
11. **Объёмы.** Строки маленькие, история ограничена 500 сессиями — полная загрузка пары при привязке устройства тривиальна; партиционирование/пагинация не нужны.

### Что это добавляет к плану изменений в коде

- `SessionSummary.id` → UUIDv7 (миграция: старым записям сгенерировать id при апгрейде).
- `updated_at` (+ `deleted_at` для tombstones) в `ProgressTopic`, `LearningItem`, `Topic`.
- Outbox-таблица + курсор `last_pulled_seq` в metadata.
- Экран пары: ветка «пара существует в облаке» (adopt vs replace).

## 8. Уточнения после сверки с кодом

Факты, которые план формулировал неточно или не знал:

- **Id тем curriculum придумывает LLM**, код их из названий не строит. `sanitize_curriculum_ids` срабатывает только как repair при падении JSON-парса; пустые id заменяются на `"topic"`, коллизии новых тем из анализа — суффиксами `-1`/`-2`. Последствия: мерж прогресса по «совпавшим id» при конфликте curriculum менее надёжен, чем предполагал камень №1; id нестабильны между машинами и между регенерациями. Опциональное усиление: канонизировать id в коде (детерминированный слаг из названия) при генерации, а не доверять LLM.
- **`config.json` хранит API-ключи провайдеров в открытом виде.** Токен доступа лежит отдельно в `~/.open-course-cli/auth.json` с правами `0600` (как `~/.aws/credentials`). Keychain сознательно отключён: для неподписанного/обновляемого бинарника macOS показывает системные запросы доступа к связке ключей, а молчаливый fallback приводил к потере токена («unauthorized» сразу после логина).
- **Reviews хранят полные тексты** конспектов (`TopicReview.content`) — решение «не синкаем» экономит заметный объём, верно.
- **Тексты упражнений и ответы пользователя на диск не пишутся вообще** (только в памяти `MentorSession`), кроме debug-дампов промптов при `OPEN_COURSE_CLI_DEBUG` — их тоже стоит явно упомянуть в списке «не синкается».
- **Отдельной сущности «пара» в БД нет**: изоляция пар — через файловую систему (`.open-course-cli/pairs/{pair_id}/db`), в таблицах пара — только поля `native_lang`/`target_lang`. На сервере `pair_id` становится первоклассным ключом партиционирования — это изменение модели, а не только перенос схемы.
- **У `Topic` уже есть поле `version: i32`** — для версионирования канонического curriculum можно опираться на него, а не вводить новое.
- **Сбросы:** `learning_items` не сбрасывается ни одним `ResetAction` (ни точечно, ни в `All`); `progress.reset()` стирает и metadata. См. камень №5.

## 9. Открытые вопросы, которые план пока не закрывает

### Безопасность и жизненный цикл токенов

- Срок жизни access token, refresh/rotation, поведение CLI при 401 (просрочен/отозван) — сейчас план говорит только «получает access token». Нужен флоу повторного логина и потерянного refresh.
- Device flow детали: TTL device-кода, интервал и лимит поллинга, поведение при истёкшем коде.
- Авторизация на сервере нигде не описана: каждый запрос обязан проверять, что `pair_id` принадлежит `user_id` из токена. Плюс rate limiting и лимиты размера push — протокол публичный (sync-крейт открыт), абьюз неизбежен.

### Биллинг — упомянут как цель, но не спроектирован

- Провайдер платежей (Stripe/Paddle), webhook → entitlement, эндпоинт `GET /v1/me` со статусом подписки.
- Поведение при истёкшей подписке: sync становится read-only? Сколько хранятся данные после отписки? Это нужно ответить пользователю в UI до первого пуша.
- LLM-квоты серверных сессий для мобилки (токены/день, деградация при превышении).

### Удаление аккаунта и GDPR

- `DELETE /v1/account` (+ локальный wipe токена и outbox), экспорт данных пользователя, сроки хранения tombstones и удалённых аккаунтов, privacy policy. Для open-source продукта, где данные покидают машину, это блокер релиза, а не «потом».

### Совместимость версий клиент ↔ сервер

- CLI обновляется независимо от сервера. Нужна политика: только аддитивные serde-изменения DTO, минимальная поддерживаемая версия клиента, понятная ошибка «обновите CLI» вместо молчаливого слома sync.
- Миграция локальной схемы LanceDB при апгрейде (новые `updated_at`/`deleted_at`, UUIDv7): сейчас versioned-миграций нет вообще (версионируется только `config.json`) — нужен миграционный слой для таблиц пары.

### Первая привязка устройства к существующей облачной паре

План покрывает конфликт curriculum (adopt/replace), но не мерж **прогресса** машины B, у которой уже есть свои сессии и mastery:

- Сессии B — append-only, пушатся без проблем.
- Progress B: локальные `updated_at` новее облачных → LWW перетрёт облачные значения локалью B. Это желаемо? Предлагаемый флоу при adopt: выбор «объединить» (LWW-мерж) или «начать с облачного» (локальный прогресс архивируется/отбрасывается).

### Надёжность sync-клиента

- Pull-on-start не должен блокировать запуск CLI: короткий таймаут (2–3 с) и уход в фон, иначе офлайн-старт тормозит.
- Атомарность push-батча: сервер применяет транзакционно или построчно? Порядок операций в outbox имеет значение (curriculum перед progress, tombstone — после upsert'ов в том же батче).

### Явно зафиксировать: что НЕ синкаем

- Настройки и BYOK-ключи — никогда (даже в будущем).
- Reviews (решено), debug-дампы, outbox/курсоры — служебное локальное.

### Серверные сессии для мобилки (`/v1/session/*`)

В «Порядке работ» есть, дизайна нет: стейтлесс-генерация упражнений vs серверное состояние сессии, стриминг, отказы LLM-провайдеров, кэширование. Предложение: явно вынести в «Фаза 2» с отдельным планом, в MVP сервер — только auth + sync + billing.

### Операционка сервера

Хостинг/деплой, миграции Postgres, бэкапы и retention, логи (без учебного контента), мониторинг. Минимум для MVP: managed Postgres + nightly backup + healthcheck + алерт на ошибки sync.

### Тестирование

- Контрактные тесты протокола: публичный sync-крейт против mock-сервера; сервер против golden-фикстур DTO (защита от serde-несовместимости).
- Тесты конфликтов: adopt/replace, tombstone-reset на двух устройствах, дубли пушей, часы в будущем.
- Интеграционный сценарий «две машины»: два CLI-профиля против локально поднятого сервера.
